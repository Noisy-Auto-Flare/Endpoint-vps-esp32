# Шпора — монорепозиторий

Три устройства + бэкенд, работающие вместе: **ESP32-CAM** (фото заданий на уроке) → **Backend** (отправка в Gemini AI) → **microReader** (получение ответа), плюс **ESP32-C3 микрофон** (голосовые вопросы).

```
┌─────────────┐     ┌──────────────┐     ┌──────────────┐
│  ESP32-CAM  │────▶│   Backend    │────▶│  microReader │
│  (фото)     │     │  (Gemini AI) │     │  (ответ)     │
└─────────────┘     └──────────────┘     └──────────────┘
┌─────────────┐     └───────▲──────┘
│ ESP32-C3    │────▶        │
│ (микрофон)  │     чанки по│ 5 сек, склейка на сервере
└─────────────┘             │
```

## Компонент 1: ESP32-CAM

### Что делает
- Короткое нажатие кнопки: снять ОДИН кадр и сразу отправить его в стейджинг на сервере (без вспышки, без миганий)
- Удержание кнопки (≥1.5 с): коммит — все кадры стейджинга уходят в Gemini разом (без миганий)
- Старый burst-путь (до 10 фото в памяти платы, отправка разом) остался в веб-странице как запасной для непрошитого CAM
- LED полностью тихий: единственная индикация — через 2 с после подключения к Wi-Fi один длинный + один короткий миг (плата жива и в сети). Все успехи/ошибки — только в Serial-лог с HTTP-кодом

### Настройка
1. Скопируй `esp32-cam/ESP32_CAM_recorder/config.example.h` → `config.h`
2. Заполни реальными данными (Wi-Fi, адрес сервера, ключ)
3. Залей прошивку ESP32_CAM_recorder.ino через Arduino IDE
   - Плата: AI Thinker ESP32-CAM
   - Partition Scheme: Huge APP (3MB No OTA/1MB SPIFFS)
   - PSRAM: Enabled

### Использование
| Действие | Результат |
|----------|-----------|
| **Короткое нажатие** кнопки | Кадр сразу уходит на сервер (`POST /api/photo-frame`), без индикации |
| **Удержание** кнопки (≥1.5 с) | Коммит стейджинга в Gemini (`POST /api/photos/commit`), без индикации |
| Подключение к Wi-Fi | Через 2 с: один длинный + один короткий миг (плата в сети) |
| Ошибки / успех | Только в Serial-лог с HTTP-кодом (200/400/429/413/502), LED молчит |

## Компонент 2: Бэкенд (Flask)

Посредник между устройствами и Google AI Studio (Gemini API).

### Быстрый старт на VPS

```bash
# 1. Python и venv
sudo apt update && sudo apt install -y python3 python3-venv python3-pip

# 2. Клонируй репозиторий и зайди в папку
cd Endpoint-vps-esp32

# 3. Виртуальное окружение
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt

# 4. Настрой .env
cp .env.example .env
nano .env   # впиши GOOGLE_API_KEY и придумай DEVICE_KEY, при желании поменяй PORT

# 5. Тестовый запуск (.env подхватывается сам через load_dotenv)
python3 app.py
```

### Порты
Порт задаётся в `.env` (переменная `PORT`, по умолчанию 8080). Можно переопределить:
```bash
python3 app.py --port 8090
```

Проверка:
```bash
curl http://ТВОЙ_IP:8080/api/health
# {"status":"ok","model":"gemini-3.5-flash-lite"}
```

### Эндпоинты

| Метод | Путь | Описание |
|-------|------|----------|
| GET | `/api/health` | Проверка сервера (без ключа) |
| POST | `/api/photo-frame` | Принять 1 JPEG-кадр в стейджинг (без отправки в Gemini) → `{"ok":true,"staged":N}`; ошибки: `400` пустое тело, `413 frame too large` (лимит `PHOTO_FRAME_MAX_BYTES`), `413 staging full` (лимит `PHOTO_STAGING_CAP`), `413 staging bytes full` (лимит `PHOTO_BYTES_CAP`) |
| POST | `/api/photos/commit` | Отправить все staged-кадры в Gemini разом → `{"ok":true,"frames":N,"text":...}`; ошибки: `400` стейджинг пуст, **`429` коммит уже идёт**, `502` Gemini недоступен (кадры НЕ чистятся — можно повторить) |
| GET | `/api/photo-status` | Статус стейджинга для microReader: `{"staged":N,"photo_status":"...","answer_ready":bool,"voice_busy":bool}` (компактный JSON без пробелов). `photo_status`: `idle`/`staged`/`sent_to_llm`/`txt_ready`/`consumed`/`error`. `answer_ready=true` — есть незабранный ответ в любом из двух слотов (см. честный `answer_ready` ниже); после неудачного коммита свежие ответы не предлагаются, пока коммит не пройдёт. `voice_busy=true` — идёт обработка голосового финала (склейка + Gemini). В режиме записи урока дополнительно: `voice_mode`, `lesson_chunks` (чанков в активной записи, а при её отсутствии — чанков последнего завершённого урока; 0 только при старте) |
| POST | `/api/photo` | Legacy: одиночное JPEG-фото сразу в Gemini (для старой прошивки/веб-страницы); ошибки: `400`, `413 photo too large` (лимит `PHOTO_MAX_BYTES`), `502` |
| POST | `/api/photos` | Legacy: серия фото (JSON с base64) сразу в Gemini (для старой прошивки/веб-страницы); ошибки: `400`, `413` (`too many images` / `images too large`), `502` |
| POST | `/api/voice` | Принять WAV-аудио целиком, отправить в Gemini; ошибки: `400`, `413 voice too large` (лимит `VOICE_MAX_BYTES`), `502` |
| POST | `/api/voice-chunk` | Принять WAV-чанк (5 сек) от ESP32-C3; при `X-Final: true` склеить сессию и распознать речь: Groq Whisper → текст → Gemini (резерв: аудио сразу в Gemini). Ошибки: `400` (нет `X-Session-Id`, плохой индекс, дырки в чанках), `413 chunk too large` (лимит `VOICE_CHUNK_MAX_BYTES`), `413 too many sessions` (лимит `VOICE_MAX_SESSIONS`), **`413` слишком много чанков — сессия сбрасывается** (лимит `VOICE_MAX_CHUNKS`), `502` |
| GET | `/api/voice-mode` | Текущий режим голоса: `{"mode":"qa"|"lesson"}` (глобальный режим в памяти процесса) |
| POST | `/api/voice-mode` | Переключить режим голоса: JSON `{"mode":"qa"|"lesson"}` → `{"ok":true,"mode":"lesson"}` |
| GET | `/api/latest` | Отдать newest ready из двух слотов (фото + голос) **однократно** — потребляется только отданный слот, второй остаётся. Поле `source`: `photo` / `photos_burst` / `photos_commit` / `voice` / `voice_chunks` / `voice_stt`. Голос не затирает фото и наоборот; повторный опрос — `ready:false` |

Все эндпоинты (кроме `/api/health`) требуют заголовок `X-Device-Key`, без него — `401 unauthorized`. Тело больше `MAX_CONTENT_LENGTH` → `413 request too large` на любом эндпоинте.

### Проверка вручную

```bash
# Отправить фото
curl -X POST http://ТВОЙ_IP:8080/api/photo \
  -H "X-Device-Key: твой_device_key" \
  --data-binary @test.jpg

# Отправить аудио
curl -X POST http://ТВОЙ_IP:8080/api/voice \
  -H "X-Device-Key: твой_device_key" \
  --data-binary @test.wav

# Забрать ответ
curl http://ТВОЙ_IP:8080/api/latest \
  -H "X-Device-Key: твой_device_key"
```

### Распознавание речи (STT)

Голосовые сообщения по умолчанию идут **напрямую в Gemini**: склеенное аудио → ответ. Опционально можно включить **Groq Whisper**: склеенное аудио → расшифровка в текст → текст в Gemini (лучше на шумных записях). Если Groq включён, но ключ не задан или сервис недоступен — автоматический возврат на прямой путь.

Переменные `.env`:

| Переменная | Значение |
|---|---|
| `GROQ_STT_ENABLED` | `false` (по умолчанию, прямой путь) или `true` (через Groq) |
| `GROQ_API_KEY` | Ключ с https://console.groq.com/keys (есть бесплатный тариф). Пусто = прямой путь |
| `GROQ_STT_MODEL` | `whisper-large-v3` (точнее) или `whisper-large-v3-turbo` (быстрее) |
| `GROQ_STT_LANGUAGE` | Язык распознавания, по умолчанию `ru` |

Какой путь сработал — видно в ответе финального чанка (`"stt":"groq"` / `"stt":"gemini_direct"`) и в journalctl (`[stt] ...`, `source=voice_stt`).

### Лимиты

| Лимит | Дефолт (env-knob) | Кто ограничивает |
|---|---|---|
| `MAX_CONTENT_LENGTH` | 8388608 (8 МБ) | Бэкенд: app-wide cap тела запроса; больше → `413 request too large` |
| `PHOTO_FRAME_MAX_BYTES` | 2097152 (2 МБ) | Бэкенд: один кадр `POST /api/photo-frame`; больше → `413 frame too large` |
| `PHOTO_STAGING_CAP` | 20 кадров | Бэкенд: лишний `POST /api/photo-frame` → `413 staging full` |
| `PHOTO_BYTES_CAP` | 12582912 (12 МБ) | Бэкенд: суммарные байты стейджинга; больше → `413 staging bytes full` |
| `PHOTO_STAGING_TTL` | 1800 сек | Бэкенд: просроченные кадры сгорают при входе frame/commit (`idle` при пустом) |
| `PHOTOS_MAX_IMAGES` | 10 | Бэкенд: макс. картинок в `POST /api/photos`; больше → `413 too many images` |
| `PHOTOS_MAX_TOTAL_B64` | 6291456 (6 МБ) | Бэкенд: суммарный base64 в `POST /api/photos`; больше → `413 images too large` |
| `VOICE_CHUNK_MAX_BYTES` | 1048576 (1 МБ) | Бэкенд: один чанк `POST /api/voice-chunk`; больше → `413 chunk too large` |
| `VOICE_MAX_CHUNKS` | 20 чанков (~100 сек при чанках по 5 сек) | Бэкенд, env-knob (`VOICE_MAX_CHUNKS`, дефолт 20): лишний чанк → `413`, сессия сбрасывается |
| `LESSON_MAX_CHUNKS` | 2000 чанков (~2.7 ч при чанках по 5 сек) | Бэкенд, env-knob (`LESSON_MAX_CHUNKS`, дефолт 2000): лимит чанков в режиме записи урока; общий `VOICE_CHUNK_MAX_BYTES` и TTL сессий |
| `VOICE_SESSION_TTL` | 600 сек | Бэкенд, env-knob (`VOICE_SESSION_TTL`, дефолт 600): сессия без финального чанка сгорает (чистка при следующем чанке) |
| `VOICE_MAX_SESSIONS` | 50 | Бэкенд: макс. голосовых сессий в `POST /api/voice-chunk`; больше → `413 too many sessions` |
| `VOICE_MAX_BYTES` | 2097152 (2 МБ) | Бэкенд: целиком `POST /api/voice`; больше → `413 voice too large` |
| `PHOTO_MAX_BYTES` | 2097152 (2 МБ) | Бэкенд: целиком `POST /api/photo`; больше → `413 photo too large` |
| `MAX_ANSWER_CHARS` | 8000 | Бэкенд: обрезка текста ответа в обоих слотах (`set_latest_result`, фото+голос); не `413` |
| `MAX_SECONDS` | 7200 сек (2 ч, 1440 чанков по 5 сек) | Прошивка ESP32-C3 (`microphone.ino`): жёсткий лимит ОДНОЙ записи; в режиме урока одного нажатия в начале и одного в конце хватает на весь урок |
| `UPLOAD_QUEUE_LEN` | 8 чанков | Прошивка ESP32-C3 (`microphone.ino`): очередь отправки чанков; старт записи отклоняется, пока она не пуста |
| `UPLOAD_RETRIES` | 3 попытки | Прошивка ESP32-C3 (`microphone.ino`): повторов отправки одного чанка при ошибке (пауза между попытками 2000 мс, `UPLOAD_RETRY_PAUSE_MS`); при полном провале файл остаётся в SPIFFS до очистки при загрузке, запись продолжается, ошибка — в Serial |
| `BURST_MAX_PHOTOS` | 10 кадров | Прошивка ESP32-CAM (буфер серии в памяти платы, legacy burst-путь) |

Все лимиты сервера — env-knob'ы, меняются через `.env` (см. `.env.example`).

Параллельный коммит запрещён: второй `POST /api/photos/commit` во время идущего возвращает `429 commit already in progress`.

Честный `answer_ready`: после неудачного коммита (`502`, кадры НЕ чистятся — можно повторить) старые незабранные ответы НЕ предлагаются (`answer_ready=false`, `GET /api/latest` отдаёт `ready:false`), пока следующий коммит не пройдёт успешно. Успешный коммит снимает подавление.

Стартовый guard: без `GOOGLE_API_KEY` или с плейсхолдером `DEVICE_KEY` (`""` / `"change-me"`) процесс падает на старте (`sys.exit`) — сначала заполни `.env`.

### systemd

```ini
[Unit]
Description=Shpora backend
After=network.target

[Service]
Type=simple
User=твой_юзер
WorkingDirectory=/путь/до/Endpoint-vps-esp32
EnvironmentFile=/путь/до/Endpoint-vps-esp32/.env
# workers=1: всё состояние живёт в памяти процесса (слоты ответов, стейджинг кадров, голосовые сессии, мьютекс коммита) — второй воркер его не увидит; параллелизм дают треды.
ExecStart=/путь/до/Endpoint-vps-esp32/venv/bin/gunicorn app:app --workers 1 --threads 8 --timeout 150 --bind 0.0.0.0:$PORT
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

`$PORT` подставляется systemd из `.env` (строка `PORT=...`). `timeout 150` — с запасом под склейку чанков + Groq STT + Gemini (10–25 с).

> Для локальной отладки остаётся `python3 app.py` (ветка `if __name__ == "__main__"`, `threaded=True` обязателен — финал чанка занимает 10–25 с). `app.py` читает `.env` сам через `load_dotenv`, `export` не нужен (флаг `--port` имеет приоритет над `PORT` из `.env`).

```bash
sudo systemctl daemon-reload
sudo systemctl enable shpora-backend
sudo systemctl start shpora-backend
sudo systemctl status shpora-backend
```

## Компонент 3: microReader

### Что делает (v1.3, три меню)
- Вход из главного меню — **удержание ВНИЗ**. WiFi в меню ответов не используется и гасится на любом выходе.
- **Меню 2 "ОТВЕТЫ"**: строка 0 — "Мониторинг", далее файлы `answer_*.txt` списком **новые → старые** (максимум 40 в списке, держатся новейшие). OK на файле — открыть штатным ридером; OK на "Мониторинг" — переход в Меню 3. **UP-hold / DOWN-hold — выход в главное меню.**
- **Меню 3 "Мониторинг"**: строка 0 — тумблер "Мониторинг: ВКЛ/ВЫКЛ" (включает WiFi вручную), ниже — живые строки статуса. Во включённом состоянии опрашивает `GET /api/photo-status` **раз в 2 с** (`кадров на сервере: N`, `ответ получен` / `ошибка сервера` / `ошибка wifi`, `голос: думаю...` пока `voice_busy=true`). Если ответ готов — **OK забирает его через `GET /api/latest`**, сохраняет как следующий `answer_N.txt`, мониторинг остаётся ВКЛ. **UP-hold — назад в Меню 2**, DOWN-hold — выход в главное меню.
- Два слота ответов: `GET /api/latest` отдаёт newest ready из слотов фото/голос и потребляет только его (голос не затирает фото), повторный опрос вернёт `ready:false`.

> Непрошитые устройства (v1.2): там single-shot — удержание ВНИЗ в главном меню сразу опрашивает `GET /api/latest` и сохраняет ответ, без меню ответов и мониторинга.

### Прошивка

Актуальная версия: **v1.3** (`microreader/firmware/a-microReader-v1.3/`, меню ответов + мониторинг).
Готовый бинарь: `microreader/firmware/a-microReader-v1.3.bin` (в гит не коммитится, собирай локально).

1. Открой `microreader/firmware/a-microReader-v1.3/a-microReader-v1.3.ino` в Arduino IDE
2. Ядро ESP8266 **v3.1.2** (как у оригинала [Nich1con/microReader](https://github.com/Nich1con/microReader))
3. Скопируй библиотеки из оригинального репозитория (`libraries/`) в свою папку libraries с заменой
4. Плата **Generic ESP8266 Module**, точные настройки (проверены по `boards.txt` ядра 3.1.2):
   - Upload Speed: 921600, CPU Frequency: 80MHz
   - Flash Size: **4M (FS:2MB OTA:~1019KB)** — это чип 4 МБ: скетч до 1 МБ, OTA-слот ~1019 КБ, FS 2 МБ (0x200000–0x3FA000)
   - Остальное по умолчанию; для первой прошивки с другой разметки — Erase Flash: All flash
5. Залей прошивку (наш `.bin` ~500 КБ < 1019 КБ — в OTA-лимит входит с запасом)

> ⚠️ **Важно**: если файловая система показывает ~64 КБ вместо 2 МБ — прошивка была собрана с неверным `Flash Size` (например, 1M-вариант с FS 64K). Лечится только перепрошивкой по USB один раз с `Flash Size: 4M (FS:2MB OTA:~1019KB)` и `Erase Flash: All flash` — иначе старая разметка остаётся на неверном смещении. Дальше обновляй через OTA.

### Настройка

1. Включи microReader, войди в Wi-Fi меню (удержание средней кнопки)
2. Подключись к точке доступа "Reader AP" (пароль: 00000000)
3. Открой браузер, перейди по IP, который показывает дисплей
4. Во вкладке "Подключение к сети" укажи SSID/пароль своей точки доступа
5. Во вкладке **"Сервер"** укажи:
   - **Хост бэкенда** — IP или домен твоего VPS
   - **Порт** — порт бэкенда (по умолчанию 8080)
   - **Ключ устройства** — тот же DEVICE_KEY, что в .env
6. Нажми "Сохранить"

### Получение ответа (v1.3)

1. Убедись, что microReader знает Wi-Fi STA и параметры сервера (вкладка "Сервер")
2. В главном меню **удерживай ВНИЗ** — откроется Меню 2 "ОТВЕТЫ"
3. Курсор на "Мониторинг" — нажми **OK**, в Меню 3 наведи курсор на строку 0 и нажми **OK** (тумблер → "Мониторинг: ВКЛ", WiFi подключается сам)
4. Следи за строками статуса (обновляются раз в 2 с): `кадров на сервере: N`, при готовности — `ответ получен`
5. Нажми **OK** — ответ заберётся через `GET /api/latest` и сохранится как следующий `answer_N.txt` (мониторинг остаётся ВКЛ, можно ждать следующий)
6. **UP-hold** — назад в "ОТВЕТЫ", открой файл штатным ридером и читай

> v1.2 (непрошитые): в главном меню **удерживай ВНИЗ** (≥1.5 с) — single-shot опрос `GET /api/latest`, дисплей покажет "Ответ получен! Сохранено как: /answer_N.txt".

## Компонент 4: ESP32-C3 микрофон

### Что делает
- Записывает голос **чанками по 5 секунд** по нажатию кнопки (одно нажатие — старт, второе — стоп). Жёсткий лимит одной записи — **2 часа** (`MAX_SECONDS=7200` в `microphone.ino`): одно нажатие в начале урока, одно в конце. Ограничение сервера в режиме `qa` — **20 чанков на сессию** (`VOICE_MAX_CHUNKS=20`); в режиме урока — до **2000 чанков** (`LESSON_MAX_CHUNKS=2000`), поэтому урок пишется в один WAV без обрыва.
- Каждый чанк сразу отправляется на бэкенд (`POST /api/voice-chunk`)
- Отправка каждого чанка: до 3 попыток с паузой 2000 мс (`UPLOAD_RETRIES=3`, `UPLOAD_RETRY_PAUSE_MS=2000` в `microphone.ino`); если все попытки провалились, файл чанка остаётся в SPIFFS до очистки при следующей загрузке, запись продолжается, ошибка фиксируется строкой в Serial-логе
- Сервер накапливает чанки сессии, при финальном чанке склеивает их в один WAV и отправляет в Gemini
- Ответ попадает в голосовой слот `GET /api/latest` (фото и голос — два независимых слота, голос не затирает фото) — microReader забирает newest ready через Мониторинг → OK (`answer_N.txt`)
- LED: на старте записи — один длинный миг, постоянно не горит (по умолчанию `LED_SOLID_WHILE_RECORDING=false`); 3 мига — успех, 2 — ошибка отправки (только на финальном чанке; промежуточные неудачи — только Serial), 5 — критическая (SPIFFS/нет Wi-Fi)
- Старт записи отклоняется (2 мига), если чанки предыдущей записи ещё уходят (очередь отправки не пуста, `UPLOAD_QUEUE_LEN=8`)
- При загрузке очищается SPIFFS от недоотправленных `/c*.wav` обходом каталога (а не перебором всех имён)

### Прошивка

1. Открой `esp32-c3/microphone/microphone.ino` в Arduino IDE
2. Скопируй `config.example.h` → `config.h` и заполни (Wi-Fi, IP сервера, порт, DEVICE_KEY)
3. Плата: ESP32C3 Dev Module, Flash Size: 4MB, Partition: Default 4MB
4. Залей прошивку

### Подключение (MAX4466 → ESP32-C3 SuperMini)

| MAX4466 | ESP32-C3 |
|---------|----------|
| OUT | GPIO4 |
| VCC | 3V3 |
| GND | GND |

Кнопка — встроенная BOOT (GPIO9). LED-индикация на GPIO8 (встроенный, активный LOW).

### Питание от аккумулятора

```
Li-ion 3.7V → повышающий модуль (boost) → 5V → пин 5V платы
                                       GND → GND платы
```
Поставь конденсатор 100–470 мкФ на выходе повышайки, чтобы убрать пульсации (микрофон сидит на ADC).

### Использование

| Действие | Результат |
|----------|-----------|
| Нажатие кнопки (старт) | Запись началась (один длинный миг LED, LED не горит постоянно), чанки по 5 сек уходят на сервер; старт отклоняется (2 мига), если чанки предыдущей записи ещё уходят |
| Нажатие кнопки (стоп) | Последний чанк уходит с `X-Final: true`, сервер склеивает и шлёт в Gemini |
| LED 3 мигания | Успех: всё отправлено |
| LED 2 мигания | Ошибка отправки / записи — только на финальном чанке; промежуточные неудачи фиксируются только в Serial и дают дыру 5 с в аудио урока |
| LED 5 миганий | Критическая ошибка (SPIFFS / нет Wi-Fi) — локальная; ошибки сервера, включая 413 (слишком много чанков, сессия сброшена), дают 2× только на финальном чанке, промежуточные чанки при неудаче — только Serial (дыра 5 с в аудио) |

### Протокол чанков

```
POST /api/voice-chunk
X-Device-Key: <ключ>
X-Session-Id: <уникальный ID записи>
X-Chunk-Index: <0, 1, 2, ...>
X-Final: true|false        # true только на последнем чанке
Content-Type: audio/wav    # тело — сырые байты WAV (16 кГц, 16 бит, моно)
```

## Режим записи урока

Второй режим голоса: друг приносит микрофон в школу, в начале урока включает запись, в конце выключает. Записи копятся на сервере в `lessons/`, без вызова Gemini — Gemini тратится потом, вручную владельцем на компьютере. Первый режим (`qa`, вопрос-ответ) остаётся по умолчанию.

### Что это
- Режимы: `qa` (по умолчанию, текущий: чанки → склейка → Gemini → ответ) и `lesson` (чанки складываются в файлы урока, БЕЗ вызова Gemini; `/api/latest` не обновляется, `answer_ready` остаётся `false`).
- Микрофон НЕ знает о режиме: он всегда шлёт чанки как обычно, решает сервер. Одна запись (старт → стоп) = одна сессия = один WAV урока; лимит одной записи в прошивке поднят до 2 часов (`MAX_SECONDS=7200`), чтобы хватило на весь урок с одного нажатия в начале и одного в конце.
- Переключение глобального режима (в памяти процесса): `POST /api/voice-mode` (`X-Device-Key`, JSON `{"mode":"qa"|"lesson"}`) → `{"ok":true,"mode":"lesson"}`; состояние: `GET /api/voice-mode` → `{"mode":"qa"|"lesson"}`.
- microReader: в Меню 3 (мониторинг) строка «Режим: Вопросы» / «Режим: Урок» с переключением по OK (при включённом мониторинге); статус-строка в режиме урока: `чанков урока: N`. `GET /api/photo-status` дополнительно отдаёт `voice_mode` и `lesson_chunks`.

### Где лежат файлы
- Директория `lessons/` рядом с `app.py` (gitignored).
- Одна сессия записи = один накопитель: `lessons/lesson_YYYY-MM-DD_HH-MM-SS_<sid>.wav` (время в имени — время ПЕРВОГО чанка, начало урока). Каждый чанк дописывается в конец, заголовок RIFF обновляется при каждом дописывании (файл не битый при обрыве питания).
- Рядом — sidecar `lessons/lesson_YYYY-MM-DD_HH-MM-SS_<sid>.json`: `{"sid":..., "started_at":..., "ended_at":..., "chunks":N, "duration_sec":...}`.

### Env-кнобы
- `LESSON_MAX_CHUNKS` — лимит чанков в режиме урока (дефолт 2000 ≈ 2.7 ч при чанках по 5 сек). Общий `VOICE_CHUNK_MAX_BYTES` и TTL сессий (`VOICE_SESSION_TTL`) действуют как обычно.

### Операционные заметки
- Режим хранится в памяти процесса и сбрасывается в `qa` при рестарте сервера — перед уроком переключи снова и проверь `GET /api/voice-mode`.
- TTL урока — idle-таймаут: чанки держат сессию живой, при обрыве Wi-Fi дольше `VOICE_SESSION_TTL` сессия сгорает и следующий чанк начнёт новый файл урока.

### Рабочий процесс
1. В microReader Меню 3 (или `curl POST /api/voice-mode`) переключи режим в `lesson`.
2. На ESP32-C3 нажми кнопку один раз в начале урока (старт — один длинный миг LED, постоянно светодиод не горит) и один раз в конце (стоп: 3 мига = финал доставлен). Одна запись = один WAV урока.
3. Скопируй каталог `lessons/` на компьютер.
4. Скармливай WAV (+ sidecar) любой LLM/Whisper самостоятельно для структурирования урока.

## Сценарий использования (на уроке)

1. Включи ESP32-CAM и microReader
2. Убедись, что оба в одной сети Wi-Fi (например, точка доступа телефона)
3. **ESP32-CAM**: нажимай кнопку коротко — каждый кадр сразу уходит в стейджинг сервера (`POST /api/photo-frame`, в ответе `{"ok":true,"staged":N}`)
4. **ESP32-CAM**: удерживай кнопку (≥1.5 с) — коммит: все staged-кадры отправляются в Gemini разом (`POST /api/photos/commit` → `{"ok":true,"frames":N,"text":...}`)
5. Подожди (Gemini обрабатывает фото, обычно 3–10 секунд)
6. **microReader**: в главном меню удерживай ВНИЗ — Меню 2 "ОТВЕТЫ" → OK на "Мониторинг" → в Меню 3 включи тумблер (OK на строке 0). Следи за `кадров на сервере: N` (опрос `GET /api/photo-status` раз в 2 с); при `ответ получен` нажми **OK** — ответ сохранится как следующий `answer_N.txt`
7. **UP-hold** — назад в "ОТВЕТЫ", открой `answer_N.txt` в ридере и читай
8. **Голос**: на ESP32-C3 нажми BOOT (старт, LED мигнёт один раз), говори, нажми BOOT ещё раз (стоп, последний чанк уходит с `X-Final: true`). Ответ ляжет в голосовой слот `GET /api/latest` — забери его так же через Мониторинг → OK. Слоты независимые: голос не затирает незабранное фото и наоборот, `/api/latest` отдаёт newest ready и потребляет только его.

> Запасной путь для непрошитого CAM: старая burst-прошивка копит серию в памяти платы (до 10 кадров) и шлёт разом в legacy-эндпоинты (`POST /api/photo`, `POST /api/photos`).

## Security notes

- **Все credentials в `.gitignore`**: `config.h` и `.env` не попадут в git
- `config.example.h` — единственный файл с credentials, который должен быть в git (с плейсхолдерами)
- Никогда не коммить `config.h` с реальными данными
- microReader хранит настройки (включая ключ устройства) в LittleFS — не открывай веб-портал на публике
- Бэкенд использует `X-Device-Key` для аутентификации — не используй простые ключи
